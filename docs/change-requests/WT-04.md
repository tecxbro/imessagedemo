# WT-04 contract requests

The macOS adapter runs against the frozen `RendererProps` and `RendererHandle`. These additions would let the compiler and the player name the same fields instead of relying on optional scene objects owned by this lane. No contract file was edited.

## 1. Message fields the pin already renders

Proposed addition to `demoMessageSchema` / `DemoMessage`:

```ts
sender: z.string().min(1).optional(),
senderInitials: z.string().min(1).optional(),
edited: z.boolean().optional(),
readAtMs: z.number().int().optional(),
reactions: z.array(z.object({
  type: z.string().min(1),
  byMe: z.boolean().optional(),
  emoji: z.string().min(1).optional(),
})).optional(),
replyTo: z.object({
  id: z.string().min(1),
  text: z.string(),
  direction: directionSchema,
  service: serviceSchema.optional(),
  sender: z.string().min(1).optional(),
}).optional(),
replyCount: z.number().int().nonnegative().optional(),
```

And on link / attachment objects: `image: z.string().optional()` and `href: z.string().optional()`.

Failing use case: a group conversation whose incoming bubble shows "Alex Morgan", an "Edited" label, a love tapback, and a reply stub. `validateDemo` drops every one of those fields, so a compiled frame cannot reproduce them.

## 2. Capture directives on the frame

Proposed sibling of `RenderFrame`, passed beside it rather than overloading `IosScreenName`:

```ts
export type MacCheckpoint = {
  conversations: Array<{
    id: string;
    contact: { name: string; initials?: string; photo?: string };
    messages: DemoMessage[];
    draft?: string;
    typing?: boolean;
    group?: boolean;
    pinned?: boolean;
  }>;
  selectedId: string;
  switchFromId?: string;
  conversationProgress?: number;
  contextMenu?: { id: string; x: number; y: number } | null;
  plusMenu?: boolean;
  menuProgress?: number;
  selectedMessageIds?: readonly string[];
  arrival?: { id: string; kind: "send" | "receive"; progress?: number } | null;
  bubbleEffect?: { id: string; kind: BubbleEffectName; progress?: number } | null;
  screenEffect?: { kind: ScreenEffectName; progress?: number; anchorMessageId?: string } | null;
  thread?: { rootId: string; open?: boolean; progress?: number } | null;
  footer?: string;
};
```

`RendererProps` would become `{ compiled, frame, checkpoint?: MacCheckpoint }`.

Failing use case: seeking a conversation switch to 50% of `macTransitions.conversation.duration`. A fresh `RenderFrame` has one contact and no progress, and mounting only the destination does not build the shell's departing pane.

## 3. Shared readiness receipt

Proposed extension of `RendererHandle`, identical for iOS and macOS:

```ts
export type ReadinessReceipt = {
  revision: number;
  ready: true;
  width: number;
  height: number;
  fontsReady: true;
  assetsDecoded: true;
  scrollSettled: true;
  fillsReady: true;
  animationsSettled: true;
  clones: number;
  ghosts: number;
};

export type RendererHandle = {
  seek(timeMs: number): void;
  readonly element: HTMLElement | null;
  readonly revision: number;
  whenReady(revision: number): Promise<ReadinessReceipt>;
  reset(): void;
};
```

`whenReady` rejects with `stale revision ${requested}; current is ${live}` when the requested revision is not the committed one.

Failing use case: a capture issued for revision 3 after the frame has moved to revision 4 must fail, and a capture must not run before fonts, images, scroll, and `--bubble-bottom` fills have settled. The frozen handle cannot express either wait.

## 4. Arrival selector in the pin

Not a contract edit. `useArrivalAnimation` in `src/components/imessage/message-motion.tsx` queries:

```ts
`[data-message-id="${id}"] [data-slot="message-bubble"]`
```

The reply stub's bubble is the first match. Proposed selector:

```ts
`[data-message-id="${id}"] [data-slot="message-bubble"]:not([data-stub="true"])`
```

Failing use case: an outgoing reply plays its send flight from the quoted stub instead of the reply bubble. This lane skips that flight rather than forking the pin.
